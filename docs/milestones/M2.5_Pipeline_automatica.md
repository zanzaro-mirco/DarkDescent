# M2.5 — Pipeline automatica

**Cosa deve succedere (Definition of Done):** su GitHub, ogni push su `main` e ogni
pull request fanno girare i test EditMode e PlayMode; un push con un test volutamente
rotto fa diventare **rosso** il job, la prova che la CI intercetta davvero i problemi.
Un tag (`m*`, `v*`) o un avvio manuale producono una **build Windows scaricabile** che
parte. Badge di stato nel README.

**Tempo stimato:** 2–4 h di sessione (piano v2.7). **Prerequisito:** M2 chiusa (tag `m2`).

**Come si lavora:** i workflow li scrivo io. A Mirco restano i secrets del repo
(credenziali che non devo vedere né digitare), la scelta delle decisioni qui sotto,
il controllo dei run su GitHub e la prova della build scaricata.

## Passo 2.5.1 — Secrets e primo run di prova

1. **Mirco**, su GitHub: *Settings → Secrets and variables → Actions → New repository
   secret*, due secrets: `UNITY_EMAIL` e `UNITY_PASSWORD`, le credenziali dell'account
   Unity con la licenza Personal. Le inserisce lui: non vanno mai in chat, nei file o
   nei log.
2. **Da verificare subito:** se l'account Unity ha la verifica in due passaggi, il
   login non interattivo del Licensing Client potrebbe fallire. Se il primo run
   fallisce sull'attivazione con un messaggio di 2FA, le strade sono un account Unity
   dedicato alla CI (gratuito, senza 2FA, con la sua licenza Personal) oppure
   disattivare la 2FA. La prima è la più pulita.
3. Io scrivo un workflow minimo, `.github/workflows/tests.yml` con solo
   `workflow_dispatch`: checkout, test EditMode. Serve a una cosa sola: vedere
   l'attivazione riuscire e la licenza tornare indietro a fine job: nel log della
   CLI di GameCI compaiono tutte e due le operazioni.

**Verifica:** run verde, e nel log l'attivazione Personal e la restituzione del posto.

**Com'è andata (3 ott 2026).** Account Unity dedicato alla CI, senza verifica in due
passaggi. Primo run rosso in 4 secondi per `coverageEnabled: false` (trappola 7). Secondo
run verde in 4 minuti: "Activation processed successfully", 11/11 EditMode,
"Successfully returned the entitlement license". Le righe d'errore sul `.ulf` mancante
alla restituzione sono il tentativo del vecchio metodo, subito seguito da quello nuovo.

## Passo 2.5.2 — Workflow dei test

`.github/workflows/tests.yml`, su `push` verso `main`, `pull_request` e
`workflow_dispatch`:

```yaml
concurrency:
  group: unity
  cancel-in-progress: false
```

Un gruppo solo per tutto il repo, non uno per branch: un push su `main` e una PR in
parallelo occuperebbero due posti della licenza (D4). E niente `cancel-in-progress`:
un job ucciso a metà rischia di non restituire il posto; il run nuovo aspetta in coda.

1. **Checkout senza LFS** (`lfs: false`), poi la lista degli oggetti LFS in un file
   (`git lfs ls-files -l | cut -d' ' -f1 | sort > .lfs-assets-id`), la cache di
   `.git/lfs` con quella lista come chiave, e solo dopo `git lfs pull`. Così un run
   che trova la cache non consuma banda LFS.
2. **Cache di `Library/`** con chiave sull'hash di `Assets/**`, `Packages/**` e
   `ProjectSettings/**`, più `restore-keys` parziali. Senza cache ogni run reimporta
   tutto il progetto da zero.
3. `game-ci/unity-test-runner@v4.4.0` con `testMode: all`, `githubToken` per le
   annotazioni dei test falliti nella pagina del run, e
   `customParameters: -assemblyNames DarkDescent.Tests.EditMode;DarkDescent.Tests.PlayMode`,
   perché i test interni dell'Input System (che è tra i `testables` del manifest) non
   girino in CI.
4. Risultati XML come artifact (`actions/upload-artifact`), conservati 14 giorni.

**Verifica:** run verde su `main` con 11 EditMode e 36 PlayMode; un secondo run trova
le cache e dura sensibilmente meno.

**Com'è andata (3 ott 2026).** Primo run completo verde in 6 minuti: 11/11 EditMode,
36/36 PlayMode (mai girati prima su Linux in Docker, nessun problema), cache LFS e
`Library/` salvate a fine job. La seconda metà della verifica, le cache ritrovate, si
vede nella PR del passo 2.5.3, che riusa le cache di `main`.

## Passo 2.5.3 — Prova del rosso

1. Un branch `ci/red-check` con un test che fallisce di proposito (un `Assert.Fail`
   in un test nuovo, non la modifica di uno esistente).
2. Pull request verso `main`: il job diventa rosso e la PR mostra il check fallito,
   con l'annotazione sul test.
3. PR chiusa senza merge e branch cancellato.

**Verifica:** schermata del check rosso nella PR; `main` resta verde. Push del branch
e apertura della PR solo con il via di Mirco.

## Passo 2.5.4 — Workflow della build

`.github/workflows/build.yml`, su tag `m*` e `v*` e su `workflow_dispatch`:

1. Stesso checkout e stesse cache del passo 2.5.2.
2. **Prima i test** (job `tests` riusato, la build ha `needs: tests`): un tag con un
   test rosso non produce build.
3. `game-ci/unity-builder@v6.0.0` con `targetPlatform: StandaloneWindows64`,
   `buildName: DarkDescent` e `versioning: None`: la versione resta il `bundleVersion`
   del progetto (0.1.0). La versione presa dal tag (`versioning: Tagged`) si valuta
   alla M3 con la prima build pubblica, perché i nostri tag (`m2.5`) non sono numeri
   di versione e potrebbero non essere accettati.
4. Cartella `build/StandaloneWindows64` come artifact `DarkDescent-Windows-<tag>`,
   conservato 30 giorni. Alla M3 lo stesso artifact andrà su itch.io.

**Verifica:** avvio manuale su `main`; **Mirco** scarica l'artifact, lo estrae e il
gioco parte sul suo PC come la build locale.

## Trappole note

1. **Un posto di licenza non restituito blocca i run successivi.** Con le licenze
   Personal il posto resta occupato finché qualcuno non lo restituisce. La CLI lo fa
   anche se il job viene annullato, ma un runner ucciso di colpo può lasciarlo
   occupato. Sintomo: "No valid Unity license" su run che prima funzionavano. Rimedio:
   restituire le attivazioni dalla pagina dell'account Unity, poi rilanciare.
2. **`actions/checkout` con `lfs: true` ignora qualunque cache** e riscarica tutti gli
   oggetti a ogni run. Va lasciato a `false` e seguito da `git lfs pull` dopo la cache.
3. **Una cache di `Library/` presa da un'altra versione di Unity o dei pacchetti**
   produce errori di import senza senso. La chiave deve includere
   `ProjectSettings/ProjectVersion.txt` e `Packages/packages-lock.json`; se succede, si
   cancella la cache da *Actions → Caches*.
4. **I secrets non arrivano alle PR da fork.** Per un progetto con un solo sviluppatore
   non conta; se un giorno arriva un contributo esterno, il suo job fallirà
   sull'attivazione e va lanciato a mano dopo la revisione.
5. **I test PlayMode girano senza grafica.** Quelli di oggi non renderizzano niente
   (la cattura per le GIF era un test temporaneo, cancellato). Un test futuro che
   legge pixel da una camera fallirebbe solo in CI: va tenuto fuori dagli assembly di
   test, come la cattura delle GIF.
6. **Percorsi con spazi** (`Assets/TextMesh Pro`) nelle chiavi di cache e nei comandi
   shell: sempre tra virgolette.
7. **`coverageEnabled: false` fa fallire il run in 4 secondi** (trovata al primo run).
   `unity-test-runner@v4.4.0` lo traduce in `--no-coverageEnabled`, ma la CLI ha il
   prefisso di negazione disattivato e il parsing strict: "Unknown argument", exit 1,
   prima ancora di scaricare Unity. La copertura si spegne con la variabile
   d'ambiente `GAME_CI_COVERAGE_ENABLED: 'false'`, che la CLI legge per ogni opzione
   con il prefisso `GAME_CI_`. Quando si aggiornano le versioni (D1), si ricontrolla.
8. **Fine riga:** i runner sono Linux. `.gitattributes` forza già `eol=lf` sui file di
   testo; un file nuovo di tipo mai visto prima va aggiunto lì.
